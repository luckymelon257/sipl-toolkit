# Асистент коректності циклічних програм (SEM-04)

Практикум (ПР 3) і Нікітченко (теореми 1.3–1.4) доводять коректність циклу так:

1. **Індукція за кількістю ітерацій.** Твердження про стан після k ітерацій (індуктивна гіпотеза) перевіряють для k = 0 (база) і для переходу k → k + 1 (крок).
2. **Вихід із циклу.** З гіпотези та хибності умови циклу виводять результат.
3. **Завершуваність.** Її доводять через додатну величину, що строго спадає (для GCD це `M + N`).

Асистент формалізує ту саму схему мовою інваріантів (логіка Хоара, найслабші передумови `wp`). Він генерує умови коректності, перевіряє кожну на станах і будує контрприклади.

## Умови коректності

Для циклу `while b do S` з інваріантом `I`, варіантом `t` і післяумовою `Q`:

| VC | Формула | У термінах курсу |
|----|---------|------------------|
| `entry` | `pre → wp(програма, post)` | база індукції: інваріант виконується перед першою ітерацією |
| `preserve` | `I ∧ b → wp(S, I)` | крок індукції: якщо `I(st)` і `fb(st) = true`, то `I(fs(st))` |
| `exit` | `I ∧ ¬b → Q` | `fb(st_n) = false` разом з інваріантом дає результат |
| `variant-bound` | `I ∧ b → t ≥ 0` | величина обмежена знизу, поки цикл працює |
| `variant-decrease` | `I ∧ b → wp(S, t < t0)[t0 ↦ t]` | величина строго спадає: цикл завершується |

Правила `wp` ([src/verify/wp.ts](../src/verify/wp.ts)):

| Оператор | `wp(оператор, Q)` |
|----------|-------------------|
| `x := a` | `Q[x ↦ a]` (підстановка) |
| `S1; S2` | `wp(S1, wp(S2, Q))` |
| `if b then S1 else S2` | `(b → wp(S1, Q)) ∧ (¬b → wp(S2, Q))` |
| `skip` | `Q` |
| `while` з інваріантом `I` | `I` плюс побічні умови з таблиці вище |

Кожна умова зберігає `derivation`: послідовність кроків `wp(Y := Y - 1, …) = …`. Тому видно, звідки взялася формула.

Умова `entry` є єдиною для всієї програми і покриває всі оператори до першого циклу. Вкладені цикли дають власні умови.

У `variant-decrease` старе значення варіанта `t0` після обчислення `wp` замінюється самим `t`, тобто значенням варіанта до ітерації. Тому `t0` не стає окремою змінною перевірки.

Якщо тіло циклу містить внутрішній цикл, умова спадання проходить крізь нього за **frame-правилом**: внутрішній цикл не змінює змінних формули, отже формула після нього лишається істинною. Якщо внутрішній цикл змінює змінні варіанта зовнішнього, асистент видає попередження V003 і не заявляє повну коректність. Хибної умови в такому разі не з'являється.

## Перевірка

Перевірка ([src/verify/verify.ts](../src/verify/verify.ts)) має три частини.

1. **Перевірка умов на кубі.** Кожна змінна умови пробігає `[lo, hi]` (за замовчуванням `[-3, 8]`, опція `--range`). Якщо станів більше за `--max-cases` (250 000), береться відтворювана псевдовипадкова вибірка. Знайдений стан, на якому гіпотеза істинна, а ціль хибна або невизначена, є **контрприкладом**. Для кроку індукції асистент виконує тіло циклу на контрприкладі й показує стан після ітерації.

2. **Прогони програми.** Програма виконується з кожного стану куба, що задовольняє передумову. Перед кожною перевіркою умови циклу асистент перевіряє:
   - інваріант («стан після k ітерацій», як у ПР 3);
   - варіант: він невід'ємний, поки цикл працює, і менший, ніж на попередній ітерації.

   Наприкінці перевіряється післяумова. Прогін вважається **непоказовим** (це не успіх і не порушення), якщо він не завершився в межах бюджету ітерацій (`--max-iterations`, за замовчуванням 10 000) або значення програми чи анотації вийшло за межі безпечних цілих чисел. Змінні, які трапляються лише в анотаціях (ghost-змінні), пробігають увесь куб, навіть якщо їх немає в передумові.

3. **Вердикт.**

   | Вердикт | Значення |
   |---------|----------|
   | `refuted` | реальне виконання з допустимого стану порушує анотацію: програма або анотація хибна |
   | `unproven` | якась умова не виконується, але жоден прогін не порушує анотацій. Зазвичай інваріант правильний, але **не індуктивний** (приклад: [not-inductive.sipl](../examples/verify/not-inductive.sipl)). Його треба посилити. |
   | `inconclusive` | нічого не порушено, але частина перевірки нічого не перевірила: якась умова вакуумна (див. нижче) або жоден прогін не вдалося оцінити. Код завершення 2. Треба розширити `--range` або збільшити бюджети. |
   | `checked-in-bounds` | усі умови виконуються на **кожному** стані куба, і всі прогони задовольняють анотації. Повна коректність заявляється, лише якщо кожен цикл має перевірений варіант. |
   | `checked-in-sample` | нічого не порушено, але частину умов або прогонів перевірено лише на вибірці (куб більший за `--max-cases`, прогони обрізано). Підсумок прямо називає, що саме вибіркове. |

Асистент окремо повідомляє про **вакуумні** умови, у яких гіпотеза жодного разу не була істинною в кубі (або ціль на таких станах не вдалося обчислити через переповнення). Такі умови фактично не перевірені, тому вердикт тоді `inconclusive`, а не `checked-*`.

## Межі автоматизації

- **Це асистент, а не доведення.** `checked-in-bounds` означає перевірку на всіх станах обмеженого куба. Загальність твердження для всіх цілих чисел потребує математичного доведення (індукції), яке студент виконує сам. Асистент дає формули цього доведення і перевіряє їх на конкретних станах.
- **Немає символьного спрощення і розв'язувача.** Формули показано так, як їх отримано підстановкою.
- **Програми з викликами функцій не підтримуються.** Для них призначений ланцюг апроксимацій (`sipl approx`).
- **Значення сполучників обчислюються зліва направо.** Порядок кон'юнктів має значення для визначеності, наприклад `Y ≥ 0 ∧ X ^ Y = …`.
